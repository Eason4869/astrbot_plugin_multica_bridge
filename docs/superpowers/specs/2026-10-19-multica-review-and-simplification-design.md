# Multica Bridge 代码审查与精简设计

日期：2026-10-19。审查基线：`main`，`f74180e7b18e86ef0d914dd26dbf9cfc3588f7c3`，版本 1.0.0。

本文件包含本次审查结论、推荐设计和验收边界。它是待用户评审的更新方案，不表示功能变更已获批准。本轮仅拉取代码、运行验证、编写文档，没有修改运行代码、配置、命令注册或线上服务。

## 1. 目标与方案选择

用户要求：读取项目并进行代码审查，列出可以精简的功能及 `/命令`，核查 LLM 自然语言识别能力边界，形成完整更新计划。

推荐定位：以 QQ 中的 Multica 连续工作对话为主，保留轻量 Issue 入口，集中在 WebUI 管理连接、工作区、项目和访问规则。

比较三个方向：

| 方向 | 好处 | 代价 | 结论 |
| --- | --- | --- | --- |
| 保持全部命令，仅修问题 | 迁移最小 | 两套入口、全局配置写操作和重复帮助继续存在 | 适合紧急补丁 |
| 工作对话为主，Issue 为高级功能，管理迁到 WebUI | 日常入口短，保留核心用途，容易控制权限 | 需要一轮兼容迁移 | 推荐 |
| 只保留工作模式，删除全部管理和 NL | 维护面最小 | 丢失已有独立 Issue 用途，更新破坏较大 | 暂不采用 |

已有仓库文档曾要求保留旧管理功能，因此此次精简先调整展示和默认入口，不能在修复版本中直接删掉旧命令。

## 2. 已确认的审查问题

### F1 / P1：普通模式自然语言绕过子命令权限

- 位置：`main.py:263-285`、`main.py:369-393`。
- 原因：事件监听器解析后直接调用 `_cmd_*`，没有检查对应 command handler 的 `enabled`、管理员过滤器和自定义授权。工作模式的 `authorize_work_event()` 没有用于该路径。
- 影响：允许接收该插件消息的普通成员，可能绕过在 AstrBot 指令管理中配置的“仅管理员”或命令禁用状态，创建资源、读取收件箱、改变全局默认工作区/项目。规则与 LLM 两种解析来源都受影响。
- 复现：`role=member`，授权钩子固定拒绝，发送 `multica 创建项目 权限探针`，创建函数仍被调用，授权钩子调用次数为 0。使用 Stub，没有真的创建项目。
- 修复：所有入口按同一 action 映射到对应命令权限；缺失映射或无法检查时拒绝执行。不能仅在 prompt 中要求模型遵守权限。

### F2 / P1：显式工作区配置错误时静默切到第一个工作区

- 位置：`multica_client.py:196-216`、`multica_client.py:232-244`。
- 原因：`_pick_workspace()` 对“留空”和“显式值未匹配”采用同一个回退；非 UUID 值随后被 `_ensure_workspace_id()` 替换为第一个工作区 ID。
- 影响：配置错拼的 slug 仍可能“连接成功”，后续创建 Issue、项目或 Chat 指向非预期工作区。
- 复现：配置 `workspace_id=typo-slug`，列表只有 `production`，解析结果却为生产工作区 ID。
- 修复：仅留空时允许自动选择；显式 ID/slug 未匹配必须报错。多个工作区且未指定时要求选择，避免依赖服务器列表顺序。

### F3 / P2：stop 被本地消息队列阻塞

- 位置：`work_mode.py:119-145`。
- 原因：发送消息和 stop 都在同一会话锁内执行，stop 无法抢占等待该锁的旧消息，也没有使旧提交失效的标记。
- 影响：用户请求停止后，原本还没提交的消息仍先提交给 Multica；网络调用或多页历史读取也会拖延停止。
- 复现：阻塞第一条消息的历史读取，排入第二条和 stop，释放后顺序固定为 `work-1 → work-2 → STOP`。
- 修复：控制操作建立独立停止屏障，使此前排队但未提交的消息失效；明确处理正在进行且结果不确定的 POST，再检查远端任务并取消。

### F4 / P2：项目名称识别与执行能力不一致

- 位置：`nl_control.py:527`、`multica_client.py:485-498`。
- 原因：规则、prompt 和 README 支持“切换到项目 前端重构”，但 `find_project()` 只匹配 ID 或至少 8 字符的 ID 前缀，不匹配 `title`。
- 影响：识别成功仍无法执行，增加 LLM 也不能补足缺失的资源解析层。工作区匹配也只支持 ID/slug，不支持名称。
- 复现：列表含 `{"id":"p1","title":"前端重构"}`，按 `前端重构` 查找返回 None。
- 修复：资源解析采用完整 ID、唯一精确名称、唯一 ID 前缀的确定顺序；多匹配返回候选，禁止自动取第一项。旧版支持范围先如实写入帮助。

### F5 / P2：规则误判会直接执行写操作，LLM 无法纠正

- 位置：`main.py:263-265`、`nl_control.py:354-453`、`nl_control.py:560-576`。
- 原因：规则一旦命中就不调用 LLM；规则不区分否定、草稿和复合意图，NL 写操作也没有确认阶段。LLM 输出仅检查 action 枚举，args 类型不对时还会转成字符串。
- 复现：`multica 创建项目 测试，先不要执行` 被识别为 `project_create`，项目名为 `测试，先不要执行`；`建个issue…然后切换项目…` 被压成一个 Issue，后半句还可能被当成 `--project`。
- 其他边界：`最近5条` 的数量被丢弃；“明天”不转成日期；姓名直接当 assignee ID；`2026-02-31` 被接受为日期文本。
- 修复：解析必须区分可执行、需澄清和非控制文本；所有 NL 写请求先生成结构化草稿，二次确认后执行；本地校验日期、枚举、数量及资源 ID。

### F6 / P2：移除触发词时破坏业务正文

- 位置：`nl_control.py:144-170`。
- 原因：关键词使用任意子串匹配，随后对整条消息进行全局替换。
- 影响：`notmultica status` 也可触发；Issue 标题、描述中的合法 `multica` 字样被删除。
- 复现：`multica 建个issue：multica 登录失败` 最终标题仅剩 `登录失败`。
- 修复：只消费被识别为调用前缀的那一次关键词及其前导礼貌词，不改动后续正文。拉丁关键词要求词边界；中文调用词使用明确前缀规则。

### F7 / P2：总开关关闭后仍可调用意图解析模型

- 位置：`main.py:255-275`、`main.py:308-366`。
- 原因：`enabled` 检查位于 LLM 解析之后；对仅提及关键词的闲聊也会尝试模型解析，而且本层没有超时、并发上限或最小调用间隔。
- 影响：关闭桥接未能关闭该模型调用路径；可能继续产生模型消耗。真实账单影响未验证。
- 复现：`enabled=False`，发送 `multica 是什么`，模拟解析器仍被调用。
- 修复：先检查启用、会话访问和可用权限，再决定是否值得调用模型；增加明确的超时和调用限制。

### 额外维护观察

- `main.py` 约 960 行，命令注册、业务、NL、配置变更和格式化混在一起；只拆与本轮相关职责，不进行全仓库重构。
- 管理 HTTP 与 Chat HTTP 的 URL 拼接、错误处理不统一；Chat 测试对认证与响应更严格，旧客户端仍直接展示服务器错误正文。
- 切换工作区没有清理旧 `project_id`，且默认选择是全局的；QQ 中的切换会影响其他窗口后续操作，并导致已有 Chat 连接指纹失效。
- 工作模式的宽泛异常分支和回传 worker 缺少足够的异常阶段日志；用户难以判断鉴权、提交和 QQ 回传哪一步失败。
- 普通模式帮助仍写 `/multica` 显示指令树；实际路由是进入工作模式。需要一处命令清单驱动帮助、页面和文档。
- 收件箱只在最新创建的 50 个 Issue 中过滤并按更新时间排序，不能保证是整个工作区最近更新的 Issue，可能漏掉较早创建但刚更新的条目。

## 3. 当前自然语言能力边界

### 3.1 两条链路

普通模式：非斜杠消息 → 包含触发词 → NL 开关/会话访问 → 规则 → 未命中才调用 AstrBot 当前 Provider 的 `text_chat()` → JSON action/args → 直接调用管理函数。

工作模式：该聊天窗口的文字 → 桥接权限和安全入口 → Multica Chat API → Multica 智能体执行 → 轮询回传。这里不使用 AstrBot 的意图解析 LLM，`nl_enabled`、`nl_llm_enabled` 不控制此链路。

### 3.2 能力清单

| 能力 | 当前结论 |
| --- | --- |
| help/status/inbox | 规则和 LLM action 都支持；`最近5条` 等非独立数字解析不完整 |
| 创建 Issue | 支持标题、描述、优先级、状态、标签等字段，但采用字符串拼参数，字段边界和否定语义不可靠 |
| 创建/列出/切换工作区、项目 | action 存在；名称解析不足；select 修改全局配置 |
| 不含触发关键词的普通消息 | 不走桥接 NL；工作模式除外 |
| 多轮补槽、纠正上次参数 | 没有插件级状态；只传当前消息，没有主动附带历史和待确认草稿 |
| 一句话多个动作 | 协议只允许一个 action，没有可靠的拆分、顺序或事务 |
| 自然语言进入/退出/新建 Chat/换智能体/停止 | 不在 NL action 集合中；工作模式内普通文字会作为任务内容转发 |
| 删除/编辑 Issue、调整已有任务、批量操作 | 桥接 NL 没有这些 action；不能因模型能理解就宣称能执行 |
| 相对日期与时区 | 规则仅识别绝对数字日期；prompt 未提供当前日期/时区，不能承诺“明天”正确 |
| 项目名/姓名转 ID | 缺少统一解析步骤，模型也没有调用资源工具来查 ID |
| 附件/图片/语音 | 工作模式明确提示不支持；普通 NL 只读取 message_str，没有可靠的附件语义处理 |
| 防越权与确认 | 当前 NL 没有复用 command 授权，也没有写前确认 |
| 模型识别成功率 | 我不确定。现有测试以规则与 JSON helper 为主，本轮没有调用真实 Provider，不能给出准确率 |
| Multica 智能体能否写代码/访问电脑/操作浏览器 | [待确认] 取决于服务端智能体、工具与运行环境，本仓库不能证明 |

LLM 当前提供“单轮管理意图分类和参数串生成”，没有实现完整的多轮代理、工具选择器或工作模式控制器。

## 4. 功能和命令精简方案

### 4.1 面向普通用户的 7 个入口

| 入口 | 计划行为 |
| --- | --- |
| `/multica` | 进入或恢复工作模式；唯一主入口 |
| `/multica exit` | 退出 QQ 接管并停止回传，不承诺取消远端任务 |
| `/multica new` | 建立新 Chat，不覆盖旧 Chat |
| `/multica agent [编号或ID]` | 无参数只展示候选；有参数才切换并新建 Chat |
| `/multica stop` | 优先停止旧排队提交并请求停止远端执行，保持工作模式 |
| `/multica status` | 统一展示模式、连接、绑定、暂停原因和任务状态 |
| `/multica help` | 展示简短主菜单及高级功能入口 |

上述六个带参数的入口均为 `/multica` 的子命令。`/multica` 本身保持进入/恢复语义，重复输入不自动退出；退出明确使用 `/multica exit`。

`stop` 和 `exit` 语义不同，保留为独立命令。文字支持、窗口隔离、来源前缀、断网不回落普通模型均保留。

### 4.2 高级能力与兼容入口

| 功能或命令 | 建议处理 | 原因 |
| --- | --- | --- |
| `/multica enter` | 保留为兼容别名，不出现在主菜单 | 与 `/multica` 重复；原进入权限条目继续作为授权锚点 |
| `/multica inbox` | 高级菜单保留 | 轻量查看进展仍有独立用途，注明查询窗口 |
| `/multica issue create` | 高级菜单保留；首层说明只展示标题、描述、优先级 | 避免要求新用户学习大量 flag；完整参数进入文档 |
| `/multica workspace list/select/create` | v1.1 保留兼容执行和权限校验，帮助改为迁移提示；新用户使用 WebUI | 低频管理和全局写配置不适合普通群聊 |
| `/multica project list/select/create` | 与工作区相同处理 | 当前容易误以为仅影响当前群 |
| 中文及 h 等命令别名 | 保留解析兼容，不铺开到主帮助 | 减少展示和文案维护，不迫使旧用户迁移 |
| 普通 NL 的工作区/项目管理 action | v1.1 返回 WebUI 管理指引，不再自动执行 | 收缩全局修改入口；显式旧命令仍有兼容路径 |
| 默认模型解析所有带关键词消息 | 只对明确的管理请求且规则不能可靠解析时调用 | 减少误触发与模型消耗 |
| 工作模式每条“已交给 Multica”回执 | 正常快速请求减少重复提示；排队、失败和较长等待仍提示 | 避免工作结果和回执双重刷屏；具体等待阈值定为 2 秒 |
| 配置总开关 + 工作转发开关 | 运行字段保留；页面主入口只突出工作转发，高级区域解释总开关 | 两者影响范围不同，直接合并会影响旧管理功能 |
| 与当前界面/README 无引用的旧 banner、divider、捐赠图片 | 搜索引用并核对打包后再清理 | 只清理已确认无用途的资源，不凭文件名删除 |

不能宣称已经物理减少了注册命令数量：v1.1 减少主菜单暴露，兼容期仍保留旧 handler。真正删除旧入口需后续大版本明确批准；本计划不设置自动删除期限。

### 4.3 NL 更新后的边界

- 普通模式支持 `help`、`status`、`inbox`、`issue_create` 和 `work_enter` 五种可执行意图。新增 `work_enter`，按明确的进入/切换语义识别口语，不要求固定说法。必须支持“进入multica模式”“进入 multica 工作模式”“切换为multica工作”“切换到 Multica 工作模式”“切到multica模式”“转到multica工作模式”“multica，进入工作模式”“帮我进入 multica 工作模式”；英文大小写、关键词与中文之间的空格不影响识别，“工作”可省略后面的“模式”。明确句由规则识别，规则无法可靠识别时才交给 LLM。
- 进入意图允许调用词位于句中或句尾：先在原始消息上识别完整的进入/切换句式，再处理普通管理指令的调用前缀。不能让通用“关键词必须在句首”的规则挡住“进入multica模式”，也不能通过全局删除关键词来迁就词序。
- 否定、询问、引用、条件表达不触发进入，例如“不要进入multica模式”“怎么切换为multica工作”“他说进入multica模式”“如果进入multica模式会怎样”；只提到 multica 或只说“开始工作”也不触发。只消费明确的单一进入意图，复杂歧义交给澄清。
- `work_enter` 必须复用 `/multica enter` 的启用状态、管理员/自定义权限及会话访问检查，并走同一安全进入流程。只确认进入意图，不能把本条消息附带的业务任务一并发送。进入失败给出明确提示并终止本条控制消息；缺少智能体选择时列候选，不宣称已进入。
- 其余工作控制保留明确子命令：`exit/new/agent/stop/status/help`；工作模式内的业务正文不重新送入普通模式 NL 解析器，避免“停止/退出”等词误触控制。
- 只读查询校验权限后执行；创建 Issue 等 NL 业务写请求生成草稿并展示工作区、项目及字段，使用 `确认 <6位短码>` 确认，或 `取消 <短码>` 取消，不新增 `/确认` 命令。明确进入工作模式不套用 Issue 草稿确认，但成功回复必须提示群共享范围、来源和退出命令。
- 草稿绑定平台实例、自身账号、窗口、发起人、连接指纹和 120 秒期限。其他成员不能确认；重复确认不能重复创建；重载后草稿失效；确认时重新授权。
- 复合动作、引用命令、询问操作方法、条件句或否定句不直接写入。能确定是在询问则放回普通对话；存在操作歧义则提问澄清。
- 使用结构化字段，禁止把模型输出直接作为可执行参数串。验证 action、类型、枚举、真实日期和资源归属；优先级限定现有四值，数量限定 1–50。
- 相对日期由本地使用 `Asia/Shanghai` 和当前日期归一化；缺少可确定含义则要求绝对日期。不让模型编造资源 ID。
- 资源名称只允许唯一精确匹配；完整 ID 优先，ID 前缀至少 8 位且必须唯一。相同名称或前缀歧义时展示候选，不自动选第一项。
- 模型解析超时 10 秒，不自动重试；同窗口最多 1 个解析请求，同用户 5 秒最多调用 1 次。关闭插件、NL 或缺少可用操作权限时，模型调用数必须为 0。
- 模型只获得完成解析所需的消息、允许的 action、当前日期和时区；不传 Token 或完整配置。解析日志不记录敏感参数正文。

### 4.4 WebUI 和配置

保留现有布局、字体、颜色体系、双语、浅色/暗色和手机适配。仅调整目标内容：主区放工作模式、智能体和当前会话；连接与高级区放工作区/项目选择及旧命令迁移说明。

新增工作区和项目列表下拉，配置提交前验证项目归属工作区。切换工作区默认清空旧项目，必须原子保存。创建工作区/项目提供通往 Multica 管理页面的入口，不为低频创建再做一套复杂表单；部署地址或深链未知时只打开已配置的服务主页。

## 6. 发布与验收策略

1. **1.0.1 安全补丁**：先处理 F1、F2、F3、F6、F7，并修正能力描述；不删除命令。NL 写操作先关闭直接写入，提示改用明确命令，直到确认流程完成。

3. **以后大版本**：仅在用户另行批准后删除弃用 handler；没有使用数据时不虚构命令频率或删除收益。

验收先看禁止的行为：未授权操作、否定句写入、跨工作区误写、过期或异人确认、停用后 LLM 消耗、stop 后旧排队继续提交都必须为 0。再验证正常创建、查询和连续对话。模型评测同时记录“正确执行/需澄清/拒绝/错误执行”，不以 JSON 可解析率代替能力正确率。

推荐发布准备包含 README、CHANGELOG、元数据、安装 ZIP、校验值和升级回滚记录。推送、建标签、发布 Release 属于后续实际实施与发布任务，本轮不执行。
